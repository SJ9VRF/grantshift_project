GrantShiftStress-testing whether personalized AI agents keep authority scoped, current, and revocable.

Personalization can persist while permission changes. GrantShift treats authorization as a lifecycle-aware capability—not a static label—and tests whether an agent keeps grants bound to the right principal, request, resource, revision, nonce, expiry, and delegation chain.

Problem
01 · Why this matters

A model can know what you want and still act without valid authority.

The hard failure is not preference prediction. It is stale, mis-scoped, replayed, expired, or delegated permission being treated as if it still authorizes the current action.

Permission changes faster than preference

A user may consistently want autonomous help while the right to act is revoked, narrowed, expired, or moved to a different task revision.

Labels hide lifecycle state

“Granted” says nothing about who granted it, for which request, on what resource, at what revision, or whether it remains valid.

Failures are costly and silent

An agent can appear helpful while executing a capability that is stale. Outcome-only task success can miss that boundary violation.

02 · Core idea

Authority is a capability with provenance and lifecycle.

GrantShift separates persistent personalization from dynamic authorization. A grant is valid only when its identity, scope, revision, freshness, replay state, and delegation ancestry still match the current action.

Novelty, precisely bounded

The contribution is not “agents need consent.” It is controlled evaluation of changing authorization under fixed preference evidence, extended to scope, provenance, expiry, replay, and delegation composition.

Falsification first

The benchmark is mutation-tested by deleting authorization invariants one at a time. A release fails if a targeted broken invariant escapes detection.

Outcome + boundary evaluation

Task success and authorization validity are graded separately, so a successful external action can still be correctly scored as unsafe or invalid.

03 · Architecture

Personalization selects intent. The capability ledger gates execution.

1 · ObservationUser history, task state, tool context
2 · Personalized policyWhat action is useful or preferred?
3 · Capability ledgerPrincipal · request · resource · revision · nonce · expiry · delegation
4 · Action gateACT / ASK / WAIT / DO NOTHING / DEFER
5 · Outcome + eventsState mutation, revoke, confirm, expire, failure
observe → propose → validate capability → act or withhold → update ledger from events
Recovery / learning loop: failed or invalid trajectories → incident mining → failure taxonomy → prioritized training/eval records → regression suite. Authorization state remains explicit rather than being silently absorbed into user preference.

05 · Experiments

Designed to break shortcuts, not reward them.

1,440capability-ledger trajectories
5,760adversarial decision steps
10capability failure families
7invariant-deletion mutants

Baselines

Latest authorization label, flat provenance matching, lifecycle-aware capability ledger, plus preference-first and static-authority controls in earlier suites.

Ablations / mutants

Ignore expiry, nonce revocation, parent revocation, request binding, principal binding, resource binding, or revision binding—one invariant at a time.

Setup

Deterministic synthetic mechanism tests, grouped counterfactual splits, bootstrap CIs and paired exact tests where applicable. External frontier-model and human studies remain separate evidence levels.

Mutation sensitivity

Every targeted broken invariant is detected: removing expiry drops exactness to 95%; removing each of six other targeted checks drops to 97.5%.

Trajectory reliability

Earlier multi-trial sandbox runs expose reliability that single averages hide: seeded action noise reduces repeated-run reliability even when pass@1 remains high.

Preference vs authorization

In the 6,000-item factorial pilot, authorization-aware conditions eliminate synthetic unauthorized ACT while preference alone does not.

07 · Failure analysis

Real failures discovered during development.

Expired grant replay
Why it failed

Flat provenance still matched principal/request/resource/revision, so an expired token looked valid.

Recovery

Capability ledger adds expiry and nonce lifecycle; replayed stale grant is rejected.

Delegation parent revoked
Why it failed

A child grant remained locally well-formed after the authority that created it was revoked.

Recovery

Ledger validates delegation ancestry before execution; descendants inherit parent invalidation.

Benchmark blind spot
Why it failed

Early mutation testing showed request, principal, resource, revision, and direct nonce mutants could still score 100%.

Recovery

Added isolation families until every targeted invariant produced a measurable regression when deleted.

Over-permissive recovery
Why it failed

An early policy asked again after a revoked delegated capability instead of rejecting the replay.

Recovery

Refined invariant: same-principal revoked replay → DO NOTHING; changed active principal → request fresh authorization.

09 · Scaling

What scales now, and what still needs real-world evaluation.

Model size

Evaluation and capability logic are model-agnostic. Current released mechanism policies are lightweight local baselines, not foundation models.

Task horizon

Atomic decisions, multi-step authorization traces, 100-turn preference drift, and repeated multi-trial sandbox trajectories.

Tool count

Local state-mutating sandbox actions. Production browser/GUI/API tools are intentionally not claimed.

Cost / latency

Released mechanism runs require no external API spend. Frontier-model latency and cost are explicitly not yet measured.

Robustness

Counterfactuals, paraphrase stress, environment shifts, provenance, lifecycle, mutation testing, repeated trials and claim-evidence gates.

Irreversible actions · Human escalation
10 · Safety / limitations

The project is strongest where it is explicit about what it does not prove.

Still unverified

Frontier-model behavior, human normative validity, production tool reliability, distribution shift in real deployments, and adversarial users.

Irreversible actions

Low-recoverability or ambiguous actions should require fresh, appropriately scoped authority; stale capability reuse is never treated as acceptable.

Human escalation

Unknown principal, conflicting grants, ambiguous scope, high stakes, or low confidence should route to ASK / DEFER / human confirmation rather than autonomous execution.

Technical report

Agent loop: observe → infer preference → resolve capability → gate action → verify outcome. Preference-learning / recovery loop: failure → incident taxonomy → targeted examples → regression eval. Training loop: exported preference pairs and reward signals are infrastructure only; no frontier post-training result is claimed.
